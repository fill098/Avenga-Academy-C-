# BUG-REPORT.md

## Ticket #1 — "Every book in our library has zero pages"

- **File / method:** `BookMapper.ToBookDto`
- **How I found it:** Stepped through the mapping method and found that `PageCount` was never assigned from the `Book` entity to the `BookDto` — the property was simply missing from the mapping.
- **What the database said:** `SELECT * FROM Book` confirmed the page counts were correctly stored (e.g. 1984 → 328).
- **What was wrong:** The mapper built the `BookDto` without copying over `PageCount`, so it defaulted to `0` regardless of what was in the database.
- **The fix:**
  - Before: `PageCount` line missing from `ToBookDto`
  - After: added `PageCount = book.PageCount` to the mapping
- **How I proved it works:** Re-ran `GET /api/books` and `GET /api/books/1` — `pageCount` now matches the value in the `Book` table (1984 → 328).

## Ticket #2 — "The author's name disappears, but only on one screen"

- **File / method:** `BookRepository.GetByAuthorAsync` (or equivalent query used by `GET /api/books/by-author/{authorId}`)
- **How I found it:** Compared the SQL generated by each endpoint. `GetByAuthorAsync` produced:
  ```sql
  SELECT [b].[Id], [b].[AuthorId], [b].[CreatedDate], [b].[Genre], [b].[Isbn], [b].[PageCount], [b].[Title], [b].[UpdatedDate], [b].[Year]
  FROM [Book] AS [b]
  WHERE [b].[AuthorId] = @__authorId_0
  ```
  Notice there is no join to `Author` at all, so the `Book.Author` navigation property stayed `null`, and the mapper fell back to `"Unknown"`. The `GET /api/books` endpoint, by contrast, already included the `Author` table, which is why it showed the correct name for the same rows.
- **What the database said:** The query above confirms no `Author` columns were being selected — the join was missing entirely.
- **What was wrong:** The by-author query never loaded the related `Author` entity, so `authorFullName` had nothing to map from and defaulted to `"Unknown"`.
- **The fix:**
  - Before: query with no `.Include(...)`
  - After: added `.Include(book => book.Author)`, producing:
  ```sql
  SELECT [b].[Id], [b].[AuthorId], [b].[CreatedDate], [b].[Genre], [b].[Isbn], [b].[PageCount], [b].[Title], [b].[UpdatedDate], [b].[Year], [a].[Id], [a].[Country], [a].[CreatedDate], [a].[FirstName], [a].[LastName], [a].[UpdatedDate]
  FROM [Book] AS [b]
  INNER JOIN [Author] AS [a] ON [b].[AuthorId] = [a].[Id]
  WHERE [b].[AuthorId] = @__authorId_0
  ```
- **How I proved it works:** Re-ran `GET /api/books/by-author/1` — `authorFullName` now correctly shows `"George Orwell"`, matching `GET /api/books`.

## Ticket #3 — "New books are created with id 0"

- **File / method:** `BookService.AddBookAsync`
- **How I found it:** Traced the `Book` object from the mapper through the service into the repository. `BookMapper.AddBookDtoToBook` correctly returns `Id = 0` (expected — the DTO has no Id). The real problem was the call:
  ```csharp
  _bookRepository.AddAsync(newBook);
  return newBook.ToBookDto();
  ```
  This call to `AddAsync` was **not awaited**. Since `AddAsync` performs real async I/O (`await _context.SaveChangesAsync()`), leaving out `await` at the call site means `AddBookAsync` doesn't pause for the save to finish — it immediately builds and returns the DTO while the insert is still running in the background. EF only assigns the real `Id` on the entity once `SaveChangesAsync` gets the identity value back from SQL Server, so at the moment `ToBookDto()` ran, `newBook.Id` was still `0`.
  This also explained the "sometimes it's there, sometimes it isn't" symptom: because the save was a fire-and-forget background task, whether it finished writing to the database before the response was sent (or before a follow-up `GET`) was a race condition. In the worst case, an exception during the un-awaited save would be silently swallowed.
- **What the database said:** Confirmed with `SELECT * FROM Book` — inconsistent presence of newly posted rows, matching the race condition.
- **What was wrong:** `AddBookAsync` called the async `AddAsync` method without `await`, so it moved on and mapped the response DTO before the database insert (and identity generation) had actually completed.
- **The fix:**
  - Before: `_bookRepository.AddAsync(newBook);`
  - After: `await _bookRepository.AddAsync(newBook);`
- **How I proved it works:** Re-ran `POST /api/books` — the response now returns the real generated `Id` (not `0`), and the `Location` header correctly points to `/api/Books/{realId}`. Confirmed with `SELECT * FROM Book` in SSMS that the row is present every time, not just intermittently.

## Ticket #4 — "Editing a book silently does nothing"

- **File / method:** `BookRepository.GetByIdAsync`
- **How I found it:** Traced the `PUT` flow and confirmed the service correctly received the updated values and called `SaveChangesAsync()` without error. The issue was upstream: the entity being updated was originally loaded via:
  ```csharp
  public async Task<Book?> GetByIdAsync(int id)
  {
      return await _context.Books
          .Include(book => book.Author)
          .AsNoTracking()
          .FirstOrDefaultAsync(book => book.Id == id);
  }
  ```
  `.AsNoTracking()` means EF's change tracker never registers this entity, so when its properties were later modified and `SaveChangesAsync()` was called, EF had no record that anything had changed and generated no `UPDATE` statement — hence `204 No Content` with no error, but nothing persisted.
- **What the database said:** The generated query confirmed the correct row was being fetched:
  ```sql
  SELECT TOP(1) [b].[Id], [b].[AuthorId], [b].[CreatedDate], [b].[Genre], [b].[Isbn], [b].[PageCount], [b].[Title], [b].[UpdatedDate], [b].[Year], [a].[Id], [a].[Country], [a].[CreatedDate], [a].[FirstName], [a].[LastName], [a].[UpdatedDate]
  FROM [Book] AS [b]
  INNER JOIN [Author] AS [a] ON [b].[AuthorId] = [a].[Id]
  WHERE [b].[Id] = @__id_0
  ```
  A follow-up `SELECT` after the `PUT` showed the row unchanged, confirming no `UPDATE` had ever been issued.
- **What was wrong:** The entity used for the update was loaded with `.AsNoTracking()`, so EF wasn't tracking changes to it and silently skipped generating an `UPDATE` statement on `SaveChangesAsync()`.
- **The fix:**
  - Before: `.Include(book => book.Author).AsNoTracking().FirstOrDefaultAsync(...)`
  - After: removed `.AsNoTracking()` so the entity is tracked by the context
- **How I proved it works:** Re-ran `PUT /api/books` with a changed title, then `GET /api/books/1` — the title now correctly reflects the update, and `SELECT * FROM Book WHERE Id = 1` in SSMS confirms the row was actually changed.

## Ticket #5 — "The year filter loses a book"

- **File / method:** Books filtering logic (`minYear` filter)
- **How I found it:** Found the filter condition:
  ```csharp
  if (minYear.HasValue)
  {
      booksDb = booksDb.Where(book => book.Year > minYear.Value).ToList();
  }
  ```
  This uses a strict `>`, so a book published in exactly `minYear` (1949) is excluded, even though the ticket asks for books published in 1949 **or later**.
- **What the database said:** N/A — this is a query-logic bug, not a data problem; the row for 1984 (Year = 1949) is present and correct in the `Book` table.
- **What was wrong:** The comparison used `>` instead of `>=`, so books published in exactly the given `minYear` were incorrectly excluded from the results.
- **The fix:**
  - Before: `book.Year > minYear.Value`
  - After: `book.Year >= minYear.Value`
- **How I proved it works:** Re-ran `GET /api/books?minYear=1949` — "1984" (Year = 1949) now appears in the results alongside every book from 1950 onward.
